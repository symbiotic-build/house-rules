# A complete minimal corpus

This synthetic example shows every authored file needed for a passing specification.
It declares one component, one literal capacity, one refusal requirement, one acceptance case and one failure state.
Its approval is teaching evidence only; it approves no production behavior.

Create the following three files in a new repository.
The JSON keys and Markdown fields use the exact [source format](formats.md#source-format).
The entry chapter includes generated navigation immediately after its opening paragraph.

## docs/example.md

```markdown

# Bounded batches

Submit one batch; a full [batcher](#batcher) refuses another item.

<!-- spec-docs:navigation document="example" -->
<!-- Generated by spec-docs; edit authored declarations. -->

## Overview

Show bounded submission and refusal.

**Audience:** Authors familiar with Markdown.

**Scope:** One synthetic submission rule.

**Non-goals:** A production service.

## Document map

- [Bounded batches](example.md#example) — Follow submission and inspect its evidence.
  - [Batcher](example.md#batcher)
  - [Decisions](example.md#decision)
  - [Open questions](example.md#questions)
  - [Reference](example.md#reference)

## Entity index

- [Batcher](example.md#batcher) (`example.batcher`) — A batcher accepts items until its batch is full.
<!-- /spec-docs:navigation -->

<a id="batcher"></a>
## Batcher

A batcher accepts items until its batch is full.

| Key | Value | Status | Basis |
|---|---|---|---|
| <a id="capacity"></a>capacity | 2 | specified | [Teaching decision](#decision) |

Submit items below [2](#capacity); a full batch retains its items on refusal.

<a id="req-capacity"></a>
### Requirement: refuse a full batch

**Actor:** [Batcher](#batcher).

**Condition:** A submitted item would exceed [2](#capacity) items.

**Result:** Return `Full` without changing the batch.

**Verification:** Inspect the batch after refusal.

**Tests:** [Full batch](#test-capacity).

**Status:** specified.

**Basis:** [Teaching decision](#decision).

<a id="test-capacity"></a>
### Acceptance test: full batch

**Method:** inspection.

**Requirements:** [Capacity refusal](#req-capacity).

**Inputs:** A full batch and one additional item.

**Expected:** `Full` and the same retained items.

<a id="failure-full"></a>
### Failure state: full batch

**Trigger:** Submission would exceed [2](#capacity) items.

**Outcome:** The caller receives `Full`.

**Retained state:** Existing items remain unchanged.

**Recovery:** Submit the item in a new batch.

**Authority:** The submitting caller may start a new batch.

**Verification:** [Full batch](#test-capacity).

<a id="decision"></a>
## Decisions

**Choice:** Use this synthetic capacity to teach declarations.

**Authority:** fixture; no production behavior is approved.

**Reason:** Demonstrate refusal and retained state.

**Rejected alternative:** An unbounded example would omit refusal.

<a id="questions"></a>
## Open questions

None; the teaching contract is complete.

<a id="reference"></a>
## Reference

`Full` means the submitted item was refused.
```

## Generate and check

Initialize Git so the checker can capture the repository input set.
Use the shared helper from the pinned House Rules revision, with its configured Python environment.
The `--fixture` option accepts this synthetic authority only; production documents use `operator` or `delegated`.

```sh
python /path/to/house-rules/skills/spec-writing/scripts/spec_docs.py generate --root /path/to/example --fixture
python /path/to/house-rules/skills/spec-writing/scripts/spec_docs.py check --root /path/to/example --fixture
```

The result is `0 errors`.
No local writing-rules file is required.
The helper reads the profile from its own House Rules revision.
The checker tests compare these fenced files with the real minimal fixture and check that fixture from an independent repository.
