FIX-NOW: a real, reachable defect with real impact (security, data loss, correctness, a contradiction of the spec or an operator decision), or waste whose fix is a deletion of a few lines. These go into the single fix round.
Design disposition takes precedence over class and severity rules below; apply [Cost and design findings](cost-and-design.md).
- ISSUE: real, but out of this PR's scope, pre-existing, or its fix would add a new mechanism or noticeably grow the PR. It becomes a separate tracked issue, not part of this PR. Describe it under "Issues to file" for the lane to file separately; external-write authority follows [External writes](external-writes.md).
- Reconcile before filing: before listing an item under "Issues to file", check the lists the dispatcher supplies: open issues, open PRs, PRs merged in the last 7 days, and issues already filed for this PR. When one of them already covers the finding, write "Already tracked as #N", "Fixed by #N" or "Being fixed in #N" in place of a new issue. If no list is supplied, the triager says so in one line and files as usual.
- Before calling a contract "unresolved", check the work item's Decisions and Pre-flight sections, the supplied repository rules part and the design; apply [Code canon](../skills/code-canon.md) for settled decisions. If a recorded decision already says what must happen and this PR's scope covers it, the finding is FIX-NOW, not ISSUE.
- Severity decides blocking: only High or Medium FIX-NOW items block. A Low finding never blocks: list it under "Accepted" marked "Severity: Low (non-blocking)" only when a fix round runs anyway for a blocking item and its fix is small; otherwise file it under "Issues to file", or reject it as NITPICK when negligible.
- Branch history is never a finding: the number of commits, their messages or their shape. The PR is merged in the repository's merge style, so the branch may hold several commits; asking to reset, rebase, squash or amend pushed commits is NITPICK.
- Deleting or weakening requirement text (a spec, design, rule or prompt sentence) is never a smallest fix and never accepted without a recorded decision ID; reviewer verdicts such as "overbuilt" or "waste" are proposals, not decisions.
- NITPICK: theoretical or very unlikely triggers with negligible impact, style, wording, preferences, or "could be stronger" without a written requirement. Rejected. A trigger that needs several independent rare conditions at once (for example a repository changing visibility mid-round AND a failing API read AND a non-default mode) is NITPICK unless it is a real security defect (someone acts without permission or secret content leaks) or loses data; say which conditions make it rare.
- FALSE: not real, not reachable, or contradicted by the design or a settled operator decision. Rejected. A failed premise check or new evidence against a settled decision is never FALSE; it is a design finding.
Complexity rule: for every FIX-NOW, give the SMALLEST fix, following [No fortification](../skills/no-fortification.md). If the only fix you can see adds a new mechanism, state, config or abstraction, classify it ISSUE unless it is security, data loss, a cost defect or a design finding. Never accept a fix that makes the PR bigger than the problem justifies; a fix whose lines are reasoned for and necessary is fine. The cost-defect definition follows [Cost defect](cost-defect.md). With a concrete operation and its count or measurement, it is FIX-NOW even if the fix adds an index, a native filter or a test.
